# Supabase MCP — making cost confirmations single-use and unforgeable (#318)

This repository is [supabase/mcp](https://github.com/supabase/mcp) at `854980b`, with the fix for [#318](https://github.com/supabase/mcp/issues/318) applied as one commit on top (`fix(mcp-server-supabase): make cost confirmations single-use and unforgeable`). That commit is the proposed PR; this file is the only other change.

## What I found

The maintainers had already shipped part of the fix: clients that support forms now get a confirmation prompt inside `create_project`/`create_branch`. Two gaps were still open, and I reproduced both with failing tests before changing any code:

| Gap | Reproduction (before the fix) |
|---|---|
| **Replay.** The signed `requestState` is stateless, so one accepted confirmation can be resubmitted until it expires (10 min). | 1 accept + 5 concurrent replays → **6 billable projects**. |
| **Forgery (legacy path).** `confirm_cost_id = sha256(cost)`, and cost comes from public pricing. | The agent hashes `{project, monthly, 10}` itself and never calls `confirm_cost` → **project created**. |

## The fix

1. **Nonce + single-use guard.** Every minted cost state carries `nonce = randomUUID()`. When a resume passes *every* other check, the server consumes the nonce exactly once, right before the create call. Replaying it returns a terminal error: "This confirmation was already used."
2. **HMAC legacy IDs.** `confirm_cost` now returns `v2.<expiry>.<HMAC(principal, expiry, cost)>`. The key is derived from the server's `requestState` key (domain-separated), or from a random key per process when no key is configured. An agent can't compute it without calling `confirm_cost`.

Files: `tools/replay-guard.ts`, `tools/cost-confirmation-token.ts` (new); small edits to `confirmation.ts`, `account-tools.ts`, `branching-tools.ts`, `server.ts`, `observation.ts`.

## Trade-offs that matter

| Decision | Why | Cost |
|---|---|---|
| **Consume before the side effect, not after.** | Consuming after a successful create leaves a race window: N concurrent replays all pass the check before any of them records it. | If the create then fails, the token is burned and the user has to confirm again. A rare re-prompt is cheaper than double billing. |
| **In-memory guard by default; pluggable `ConfirmationReplayGuard`.** | Zero setup for stdio and single-instance servers. Per-process, not per-server, because hosted builds a server per request. | **On multi-instance hosted, the default only stops replays that hit the same instance.** Hosted must pass a shared store (Redis `SET key 1 NX PXAT exp`). This is the key operational requirement of the PR. |
| **Guard fails closed when full** (10k entries). | An unbounded replay is worse than refusing a valid confirmation. | In a pathological case, users get re-prompted until entries expire. |
| **Old in-flight states/IDs aren't honored after deploy.** | A state without a nonce re-prompts instead of proceeding, and old `sha256` IDs fail. | For ≤10 minutes after deploy, some users confirm twice. No grandfathering code to maintain. |
| **Legacy path: HMAC, not consent.** | It closes the *precompute* bypass and forces every legacy confirmation through `confirm_cost`, where it's observable. | **Not fixed, and can't be on that path:** an agent can still call `confirm_cost` itself. Legacy clients have no channel to a human, so real consent needs elicitation. I state this in the PR so nobody mistakes it for a full fix. |

## Verified

- New tests: `confirmation-hardening.test.ts` (forge rejected, legit legacy flow still works, cross-cost ID rejected, replay rejected, 5-way race creates one project) and `cost-confirmation-token.test.ts` (expiry, tamper, principal and key binding, guard capacity).
- Full unit suite: **917/918 pass**. The one failure, `index.test.ts` ("fetch failed"), also fails on the untouched base commit.
- Built and tested on `5e6e6cd`. The repo's own supply-chain policy (packages must be at least 7 days old) blocks installing `main`'s current lockfile until ~Nov 19. The patch applies cleanly to `main`, and every touched file except `server.ts` is identical between the two commits; `server.ts` merged without conflicts. **Re-run `pnpm test` on `main` before opening the PR.**

## Not in scope

`execute_sql`, `apply_migration` and notebook confirmations use the same stateless signed state, so they very likely have the same replay class. A replayed destructive SQL confirmation would re-run the query. I didn't test this. Proposing it as a follow-up keeps this PR small enough to review.
